Atenção: NÃO recrie o projeto do zero.

Este pedido é uma etapa de REFINAMENTO do protótipo existente. Mantenha a identidade visual, a estrutura funcional, as telas e os fluxos que já foram desenvolvidos quando eles estiverem coerentes com o projeto. Faça alterações pontuais e estruturais apenas onde indicado abaixo.

O objetivo principal agora é fazer o protótipo parecer um produto digital real e utilizável, e não uma apresentação de um site criada por IA.

## 1. Mudar a prioridade: aplicativo primeiro

O projeto deve continuar funcionando na web, mas a experiência principal precisa ser pensada como um aplicativo web responsivo, com prioridade para dispositivos móveis.

Não tratar o sistema como um site institucional tradicional.

O usuário deverá sentir que está utilizando um aplicativo de troca de hortifrúti que simplesmente está sendo executado pelo navegador.

Prioridade de experiência:

1. Mobile
2. Tablet
3. Desktop

No celular:

• usar navegação inferior quando fizer sentido;
• manter as ações principais facilmente acessíveis com o polegar;
• evitar menus excessivamente escondidos;
• utilizar listas e blocos verticais;
• utilizar espaçamento confortável para toque;
• evitar tabelas largas;
• evitar elementos que dependam de hover;
• utilizar botões e campos com tamanho adequado para toque;
• manter o conteúdo essencial visível sem exigir navegação excessiva.

A interface deve funcionar muito bem quando adicionada à tela inicial do celular pelo Safari ou navegador, criando uma experiência semelhante à de um aplicativo instalado.

No desktop, a interface deve aproveitar o espaço disponível, mas continuar sendo claramente a mesma aplicação. Não transformar o sistema em um dashboard corporativo genérico.

## 2. Reduzir a aparência de "site feito por IA"

O protótipo atual está visualmente bonito, mas alguns elementos seguem padrões muito previsíveis de interfaces geradas por inteligência artificial.

Quero eliminar essa sensação.

A interface deve parecer desenhada por uma equipe de produto que conhece o contexto de uso real.

Evitar:

• excesso de cards;
• excesso de elementos perfeitamente alinhados e simétricos;
• blocos decorativos sem função;
• excesso de gradientes;
• grandes áreas hero genéricas;
• estatísticas decorativas;
• ícones usados apenas para preencher espaço;
• excesso de sombras;
• bordas arredondadas exageradas em absolutamente todos os elementos;
• seções repetitivas seguindo sempre a mesma estrutura;
• excesso de elementos flutuantes;
• grandes títulos de marketing;
• layouts que parecem template de SaaS;
• aparência de dashboard administrativo em telas destinadas aos usuários comuns.

Usar uma composição mais natural, com hierarquia visual baseada na importância real das informações.

Nem todos os elementos precisam ter o mesmo formato, tamanho ou nível de destaque.

A interface pode ter assimetrias sutis e variações de composição quando isso melhorar a experiência.

O objetivo não é deixar o design desorganizado. O objetivo é deixá-lo humano, funcional e específico para o contexto do Centro de Troca de Hortifrúti.

## 3. Remover sinais textuais de conteúdo gerado por IA

Revisar todos os textos existentes no protótipo.

Não utilizar travessão em nenhum texto da interface.

Não utilizar caracteres, construções ou padrões de pontuação que façam o conteúdo parecer artificialmente escrito por IA.

Evitar:

• travessões;
• excesso de dois pontos;
• frases excessivamente elaboradas;
• slogans genéricos;
• textos com linguagem publicitária artificial;
• frases como "conecte, transforme e impacte";
• chamadas genéricas de startup;
• textos excessivamente explicativos;
• emojis desnecessários;
• excesso de títulos acompanhados de subtítulos explicativos;
• frases com estrutura muito padronizada.

Usar português brasileiro natural e direto.

Os textos devem parecer escritos por uma equipe brasileira que desenvolveu uma ferramenta para comerciantes e restaurantes locais.

Priorizar frases curtas, claras e funcionais.

Exemplo de direção:

Em vez de:
"Conectamos restaurantes e comerciantes para transformar excedentes em oportunidades."

Preferir algo natural e funcional como:
"Encontre alimentos disponíveis para troca."

O sistema deve comunicar sua função sem tentar parecer uma campanha publicitária.

## 4. Repensar a apresentação inicial

A existência de uma apresentação institucional pode ser mantida, mas ela NÃO deve dominar o projeto.

Caso a tela inicial apresente o projeto, torná-la muito mais simples.

Ela deve explicar rapidamente:

Centro de Troca de Hortifrúti

Uma plataforma para restaurantes e comerciantes do Centro de Abastecimento encontrarem alimentos para troca e reduzirem perdas.

Depois disso, apresentar ações claras:

Entrar
Criar cadastro

Não criar uma landing page extensa com várias seções de marketing.

O produto principal é a aplicação.

Depois do login, o usuário deve entrar diretamente na experiência do sistema.

## 5. Login

A tela de login atual está muito genérica.

Redesenhar essa tela para parecer a entrada de um aplicativo real.

Evitar o padrão visual genérico:

logo centralizada
grande card branco
fundo com gradiente
formulário central
botão gigante
elementos decorativos

Criar uma composição mais simples e própria da plataforma.

A identidade do Centro de Troca de Hortifrúti deve estar presente, mas de maneira discreta.

O login deve transmitir confiança e simplicidade.

No mobile, a tela deve aproveitar bem a altura disponível e não parecer um formulário de desktop simplesmente reduzido.

## 6. Cards de alimentos

Os cards são importantes, mas precisam parecer menos genéricos.

Como o sistema real terá fotos dos lotes cadastrados pelos usuários, o design deve ser preparado para fotografias reais de alimentos.

Não depender de imagens fictícias altamente produzidas.

A foto deve ocupar uma posição importante no card.

As informações mais importantes devem aparecer naturalmente:

Nome do alimento
Quantidade
Maturação
Tipo de publicação
Prazo
Local ou estabelecimento, quando necessário

A maturação deve ser visualmente fácil de identificar.

Não transformar cada card em um conjunto de badges coloridos.

Usar a cor apenas quando ela tiver função.

Os cards podem variar de acordo com o contexto.

Por exemplo, uma oferta pode dar mais destaque à fotografia e à maturação, enquanto uma proposta pode dar mais destaque aos pesos envolvidos na troca.

## 7. Experiência de aplicativo

Pensar cada tela como uma tela de aplicativo, não como uma seção de website.

Criar uma hierarquia clara:

Cabeçalho
Conteúdo principal
Ação principal
Navegação

No mobile, considerar uma navegação inferior com poucas opções realmente importantes, por exemplo:

Início
Trocas
Publicar
Notificações
Perfil

Não adicionar opções apenas para preencher a navegação.

A tela inicial autenticada deve mostrar o que realmente interessa ao usuário naquele momento.

Por exemplo:

Ofertas e pedidos relevantes
Trocas em andamento
Propostas recebidas
Ações pendentes

Evitar transformar a página inicial em um painel cheio de números.

## 8. Publicação de oferta ou pedido

A criação de uma publicação deve parecer um fluxo de aplicativo.

Não apresentar um formulário enorme de uma única vez.

Organizar o preenchimento de maneira natural.

O alimento deve ser escolhido a partir da lista cadastrada.

A quantidade deve ser informada em kg.

A maturação deve utilizar somente as opções:

Verde
Meio-maduro
Maduro
Muito maduro

A foto do lote é obrigatória.

A observação é opcional e complementar.

Manter a regra de que o texto livre nunca substitui as informações estruturadas.

## 9. Propostas e contrapropostas

A tela de proposta deve deixar muito claro o que cada lado oferece e recebe.

Utilizar uma composição visual simples:

OFEREÇO

[alimento]
[quantidade]

PEÇO EM TROCA

[alimento]
[quantidade]

A regra de equivalência deve aparecer de forma natural:

1 kg = 1 kg

Não transformar essa informação em um grande elemento publicitário.

Quando existir uma contraproposta, mostrar claramente que ela é uma nova versão ligada à proposta anterior.

O histórico deve permitir compreender a negociação sem parecer uma conversa de aplicativo de mensagens.

## 10. Status das trocas

Manter o fluxo definido no projeto:

Solicitado
Proposto
Contraproposto
Aceito
Aguardando encontro
Concluído

Também contemplar:

Cancelado
Não compareceu

A apresentação dos status deve ser simples.

Evitar aqueles componentes de "stepper" extremamente decorativos e genéricos.

O status atual deve ser evidente, mas o histórico precisa continuar acessível.

## 11. WhatsApp

O WhatsApp somente deve aparecer depois que a troca for aceita.

O botão deve deixar claro que serve para combinar o encontro.

Não apresentar WhatsApp como mecanismo de negociação ou confirmação da troca.

A conclusão da troca continua sendo feita dentro da plataforma.

## 12. Pesagem e conclusão

A tela de encontro deve ser extremamente funcional.

Cada parte registra o peso recebido utilizando sua própria balança.

Mostrar:

Peso combinado
Peso registrado
Diferença

A tolerância é de até 5%.

Se ultrapassar 5%, apresentar um aviso claro antes da conclusão.

A foto da balança é opcional.

Antes de concluir, mostrar o checklist obrigatório:

Embalagem adequada
Sem sinais de contaminação ou alimento estragado

A confirmação das duas partes deve ser feita dentro do sistema.

## 13. Histórico

O histórico não deve parecer uma tabela administrativa.

No mobile, utilizar uma linha do tempo ou lista de acontecimentos que permita acompanhar:

Proposta
Contraproposta
Aceite
Encontro
Pesagem
Confirmação
Conclusão
Problemas relatados

Manter data, alimento, quantidade e participantes quando essas informações forem relevantes.

## 14. Identidade visual

Manter a paleta existente baseada na identidade "Feira":

Teal principal: #2F6B5E
Coral: #E85D4E
Mostarda: #E8A33D
Off-white: #FAF6F0
Texto: #1B3D34

Entretanto, não utilizar todas as cores simultaneamente em todos os componentes.

A cor deve possuir função.

Teal para ações principais e identidade.
Coral para situações de atenção ou urgência.
Mostarda para informações de apoio.
Off-white como base.
Texto escuro para leitura.

Evitar aparência excessivamente colorida.

## 15. Responsividade real

Não simplesmente diminuir a versão desktop.

Projetar layouts específicos para mobile.

No mobile:

• navegação inferior;
• formulários em uma coluna;
• botões acessíveis;
• fotos ocupando espaço adequado;
• cards adaptados à largura;
• conteúdo prioritário primeiro;
• menos elementos simultâneos.

No desktop:

• aproveitar melhor a largura;
• permitir duas colunas quando fizer sentido;
• manter fotografias e informações organizadas;
• preservar a mesma linguagem visual do mobile.

## 16. Preparar para o produto real

O protótipo será posteriormente conectado a um backend.

Por isso, não criar elementos que dependam de conteúdo fictício permanente.

As imagens atualmente utilizadas devem ser tratadas apenas como placeholders.

A interface deve estar preparada para receber:

• fotos reais dos lotes;
• estabelecimentos reais;
• quantidades reais;
• propostas reais;
• notificações reais;
• histórico real.

Não criar funcionalidades automáticas que não fazem parte das regras do projeto.

O sistema não deve utilizar IA para identificar alimentos, classificar maturação ou realizar automaticamente o match entre usuários.

A compatibilidade deve continuar sendo apresentada de maneira simples e compreensível, baseada nos dados cadastrados.

## 17. Regra mais importante deste refinamento

Não adicionar complexidade apenas para deixar o protótipo mais impressionante.

O Centro de Troca de Hortifrúti deve parecer uma ferramenta que pessoas realmente usariam durante o trabalho.

Imagine o usuário olhando o celular rapidamente enquanto está trabalhando em um restaurante ou no Centro de Abastecimento.

Ele precisa conseguir entender:

O que está disponível
O que eu preciso
O que está acontecendo com minha troca
O que eu preciso fazer agora

sem precisar interpretar uma interface cheia de elementos.

O resultado final deve ser moderno, funcional, responsivo e visualmente marcante, mas sem aparência de template, landing page de startup ou dashboard criado automaticamente por IA.

IMPORTANTE: preservar as funcionalidades e regras de negócio já estabelecidas no protótipo. Este é um refinamento visual e de experiência de uso, não uma mudança no conceito da plataforma.
